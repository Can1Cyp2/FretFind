# d7 Issues (continuing from d6):

A list of issues I found during and before d7. Some of these have a clear fix, some are open questions I am still working through.

## 1. Autosave was sometimes treating a progression from a different tuning as one already backed up:
With auto backup switched on, a progression built in one tuning would sometimes never make it to the cloud, and the account would end up with what looked like the same progression saved over and over instead of the new one.

The cause was the key used to tell whether a device progression was already on the account. It was built from just the progressions name and how many chords were in it, which is not actually enough to tell two progressions apart: the same name and chord count can easily happen twice without meaning to, especially two attempts at the same idea played in different tunings. Whichever one reached the account first made the key look taken, so the second one was silently treated as already backed up and never uploaded, even though its actual chords (different frets, since the tuning was different) were nothing like the first.

Done: the key is now built from the actual shape of every chord in the progression, which string and fret each note came from, rather than just the name and count. A different tuning means different frets even when the chord names line up, so two progressions only count as the same now if they genuinely are, and both a manual cloud save and autosave use this same key so they always agree on what is already backed up.

## 2. Keyboard covers the tuning name field:
The same issue as d6 issue 1, this time in the tuning popup: naming a new custom tuning, or renaming an existing one, the keyboard opened over the input with nothing shifting up to make room for it.

Done: same fix as d6, the popup is wrapped in a `KeyboardAvoidingView` so it shifts up when the keyboard opens. One wrapper covers both text fields, since they both live in the same popup.

## 3. The tuning and strum buttons ran off the screen on some smaller Android devices:
Both buttons float past the right edge of the fretboard by a fixed amount, relying on whatever margin was left over from centering the board on the screen. That margin was more than enough on a wide screen, but the boards width was capped rather than scaled down, so on a narrower phone the board grew to fill nearly the whole screen and had little to no margin for the buttons so they ended up clipped by the edge of the screen.

Done: the boards width calculation now checks whether the screen is narrow enough for this to actually happen. Only then does it shrink the board by exactly the amount the buttons need and hand that space back as a reserved margin, guaranteeing they fit. On a screen wide enough to already have room to spare, which is most phones, nothing changes and the board stays centered exactly as it was before.

## 4. Octaves were bolted on after the fact, and the custom tuning bug above is the cost of that:
Not a bug but a design mistake I made a while back that only actually caused a problem now.

Octave display was not part of the original plan for how a tuning is represented, I added it as an option later once I decided showing "E2" instead of just "E" would be useful. At that point every tuning already just had a `notes` array (the pitch classes, C to B as 0 to 11, no memory of which octave), so rather than rethinking that, I bolted a second `octaves` array on next to it, one fixed number per string, and treated the two as if they would always agree with each other.

For the nine built-in tunings that was never actually tested by anything, since none of them happen to move a string far enough to cross into a different octave from Standard, so it looked correct by coincidence and I did not think about it again until building the custom tuning feature this deliverable.

The real case: the custom tuning builder let a string be stepped down note by note, E to D# to D and so on, by moving a pitch class up or down and wrapping it at 0 to 11. Nothing about that wrap knew it had crossed from one octave into the last one below it, because the octave was never actually derived from anything, it was just copied from Standard onto every custom tuning regardless of what was picked. Step the low E string down five semitones and it should land on B1, an octave and a bit below where it started. Instead it landed on "B", still carrying Standard tunings fixed octave of 2, which is B2, a note almost a full octave higher than the one actually chosen. The label was wrong and, since the same octave number is what the fretboard and the audio use to work out the real pitch to play, the sound was wrong too.

The fix (in issue 1 of the d7 plan, the octave fix for tunings) had to work backwards from that mistake: turn each strings note and octave back into one absolute semitone count, step that instead of the bare note, then split it back into a note and an octave afterwards. That is the right way to do it, but it only exists because the data was split into two loosely connected fields to begin with. If a tuning had stored one real number per string from the start, the same absolute semitone count the fix uses now, a note and an octave are just that one number read two different ways, there would have been nothing to fall out of sync in the first place and the custom tuning builder would never have been able to produce a wrong octave.

Lesson for next time: when a later feature turns out to need information a data shape does not carry (here, which octave a note is actually in), that is worth treating as a sign the shape itself is incomplete, not just a reason to bolt an extra field on next to it and hope the two stay in agreement.

## 5. The default shape for some chords is not the shape a real guitarist would reach for:
Bm is the clearest example I have seen so far. The shape the app ranks first is not the barre shape at fret 2 (x24432) that basically every guitarist actually learns as "Bm", it is instead (x20402) which is a real legitimately playable alternative, that just is not the one anyone actually associates with that chord.

The cause is that the scoring has no idea what shape is conventionally taught, it only knows what is easier to physically hold: more open strings, fewer fingers, the root in the bass (which is also very useful criterion). For a lot of chords those two things line up, the shape most players learn first usually is the easiest one too, which is exactly why the scoring works as well as it does most of the time. But the way people commonly play chords is rooted in theory and shapes, where the app does try to blend those two things, so this being not implented is a bit of an issue or undersight. Bm is a case where the code causes things to not line up, since standard tuning happens to have both the root (B, open B string) and the minor third (D, open D string) sitting right there as open strings a couple of frets apart from other chord tones, which lets the search put together a valid, fully playable voicing with fewer fingers and more open strings than the barre shape, even though the barre shape is the one every chord chart and every guitar teacher calls "Bm".

I could keep tweaking the scoring to weigh against cases like this, but I think that would just be chasing individual chords one at a time rather than actually fixing the underlying gap, which is that the app has no concept of "this is the shape people expect" separate from "this is a shape a hand can hold". 

The tradeoff I see is:
- For the current method: that chords past the most common shape, or just weird chord shapes, will be ranked well and depicted in a realistic easy-to-play way to users, even if the alternatives aren't 100% as common as they can be.
- For a method that hardcodes the common shapes: that the app will always show the most common shape, but it will be less flexible and less able to show more easy-to-play alternatives.

Getting that right for real would mean recognizing when a generated shape matches a well known, commonly taught one and nudging it up, which in practice means having that knowledge somewhere, at least partially hardcoded. I do not have the time left in the project to do that properly, so I am leaving this as a known limitation rather than a bug I am actively fixing (for now).

## 6. A chord added from 'Chords That Fit' went into the progression with no shape:
Adding a chord straight from the suggestions put its name into the progression but nothing else. Tapping its pill afterwards did nothing at all, and the chord could not be heard or strummed the way every other chord in the strip can, so it sat there as a dead entry until the user played it on the fretboard themselves.

The cause is that a suggested chord never came off the fretboard, which is how we were saving chords originally. It is worked out from the key rather than from anything the user tapped, so at the point it was added there was no shape to save and it was stored with an empty one. That was a reasonable call when suggestions were only something to read about, but it stopped making sense once the Shapes section existed, because by then there is a shape on screen: whichever voicing the user has swiped to in the breakdown (for example shape 1 of 8 or shape 5 of 8). That is the shape they are actually looking at and the one they would expect to keep.

The part that needed care is that this must not apply to the results screen. A chord tapped in the results was really played, the exact frets the user chose are the whole reason the progression remembers shapes at all, and quietly swapping those for a generated shape would lose the thing that makes the feature worth having. So the two paths have to disagree with each other on purpose rather than sharing one behaviour.

Done: the Shapes section now reports which shape is currently on screen up to the breakdown sheet, and the sheet passes that along when 'Add to Progression' is pressed. What happens with it is left to whoever opened the sheet, which is what keeps the two cases apart: the suggestions sheet saves that shape, and the results panel ignores it entirely and carries on saving the fretboard selections exactly as before. A suggested chord added this way now behaves like any other chord in the strip, its pill recalls the shape and it can be strummed. A chord with no playable shape in the current tuning still falls back to being stored without one, which is the old behaviour and the only sensible thing left to do in that case.

The shape being looked at is held in a ref rather than in state, since nothing on the breakdown needs to redraw when it changes. It is only read at the moment the button is pressed, and making it state would have meant redrawing the whole breakdown on every swipe of the shape pager for no visible benefit.

    - However, there is still an issue, when users do want to save alternate tunings of chords they make on the fretboard, or chords that are partial or weak matches, the app will still save them as they selected on the fretboard, unless they select the shape to put on the fretboard prior to adding it to the progression. 

    This is a significant limitation, and I am not sure what the best fix is yet, but I am thinking (in cases where if the user is not going through the 'Chords That Fit' feature) :
        1. a user should be able to choose whether to save the chord as listed on the fretbaord or the variant shape they are currently looking at in the breakdown. This could be a pop-up that appears after clicking add or a separate button that says 'Add Shape to Progression' or something like that.
        2. If a user is going through the results of the chord they made, and select a shape that is graded 'partial' or 'weak', the app should still save the chord as they selected on the fretboard, but it should also give them a warning that the shape they are saving is not a full match for the chord they are trying to add, and then also have a little warning triangle beside the chord in the progression.
    (There are probably cases I am overlooking, but I think this is a good start to fixing the issue, at least.)

## 7. The Progressions sheet kept freezing and it was never the renders:
Opening Progressions and trying to actually use it (save, delete, load, rename) would seem to lock up every few seconds. Closing the sheet and opening it again always got it responding for a moment before it locked up again, which confused me: a frozen render would not un-freeze just from closing and reopening the same component with the same data. It was also locking at random points in the interaction, not just when a specific button was pressed, which made it look like a render problem rather than a specific button or action, and I knew the data was fine.

I spent two earlier attempts chasing this as a performance problem (see d6 issue 4). `Fretboard`, `ProgressionManager`, `ProgressionBar` and `FitChordsModal`, were all made so they only update when needed. All of those re-renders were real problems worth fixing, but none of them were the cause of this one as the freezing continued.

After some time I found the actual cause was that the sheet was not a slow rendering issue, or data issue. It was a problem with touch handling, two separate defects in `ProgressionManager.tsx`, rather than any rendering:
1. The dark backdrop behind the sheet was a `Pressable` wrapped around the sheets content, with the content itself another `Pressable` calling `event.stopPropagation()` to stop a tap on a row from also closing the whole sheet. `stopPropagation` does nothing in React Native, touch there is a responder negotiation. So the backdrop `Pressable` sat in front of every row, every Load and Delete button and the whole scroll view and got the touch priority before they ever saw it. So the freezing behaviour I saw was actually the button needing a second tap to register and a scroll needing a second swipe scroll. The other sheets in the app (`FitChordsModal`, `ChordDetailModal`, `WalkthroughModal`) already use the backdrop as its own layer sitting behind the content instead of wrapped around it, I had supposedly just missed this one when that pattern was changed.
2. Every `ScrollView` in React Native defaults to `keyboardShouldPersistTaps="never"`, meaning the first tap that lands anywhere in it while the keyboard is open gets consumed to dismiss the keyboard, and never reaches whatever was actually tapped. This sheet has a name box at the top and turns a saved progressions name into a text box in place to rename it (autofocused, so the keyboard was open essentially every time the sheet was actually being used for something). So the very next tap on Load, Delete, or the cloud backup button after typing anything did nothing at all and had to be repeated, which explains why I noticed it took me two clicks to do things, such as it took me two clicks to delete a chord progression, that I was noticing from earlier in the session.

In addition, there was a third smaller bug in the same area: the pressable button that starts a rename wraps the rename text box itself, so tapping into the box while already renaming counted as a fresh tap on the row and restarted the rename, discarding whatever was typed

Done: the backdrop is now its own `View` sitting behind the sheet with a separate `Pressable` covering just the backdrop area, the same shape the other sheets already use, so nothing in front of the rows or buttons is stealing their taps. The `ScrollView` now sets `keyboardShouldPersistTaps="handled"`, so a tap on a real button both dismisses the keyboard and registers, instead of only doingthe first. The rename Pressable is disabled while that row is already being renamed, so moving the cursor in the box no longer resets it.

Lesson for next time: "everything freezes" is not automatically a render problem just because it may look like one, or it caused it once before (d6 issue 4). The tell I should have realized was that the same interaction sometimes worked and sometimes did not with nothing about the data changing or being an issue (backend was fine, connection was fine, data itself was fine), which points at input being dropped somewhere rather than the JS thread actually being busy or overworked. It is worth checking touch handling before reaching for the profiler again, and saving lots of time (I spent quite a bit of time on this...)
